# Ревью проекта «Диантус»

## Общая оценка

**Крепкий проект для своей задачи — заметно выше уровня «домашнего».** Видно, что его
дорабатывали по реальным замечаниям (метки `fix #N` в коде).

Сильные стороны:
- чёткая структура (роутеры / сервисы / модели), конфигурация через `.env`;
- серьёзная безопасность «из коробки»: CSRF-токены с проверкой Origin, прогрессивная блокировка входа,
  лимиты запросов (Redis), bcrypt, заголовки безопасности и CSP, закрытая документация API в `prod`;
- заказ оформляется атомарно (`SELECT … FOR UPDATE`), есть резервирование под предзаказы;
- обмен с 1С по Basic Auth со сравнением в постоянное время;
- авто-миграции с файловой блокировкой, healthcheck, Sentry, тесты.

## Что было слабым местом и исправлено

| # | Проблема | Чем грозила | Исправление |
|---|---|---|---|
| 1 | Сессия целиком в cookie (≈ 4 КБ) | Корзина оптового клиента 10–15 позиций не помещалась: cookie отбрасывалась, клиента «выкидывало» | Серверные сессии в Redis (`app/session.py`) + тест |
| 2 | Фиксация сессии (id не менялся при входе) | Перехват/подсовывание сессии | Новый идентификатор при входе и выходе |
| 3 | Невалидный `SECRET_KEY` → каждый воркер генерировал свой | Случайные «разлогины» при нескольких воркерах | В `prod` — понятная ошибка и остановка |
| 4 | Данные пользователей вставлялись в HTML писем и PDF без экранирования | HTML-инъекция в письмо админу; чтение файлов/запросы наружу через PDF-генератор (SSRF) | Экранирование везде, ограничение `link_callback` только папкой `static` |
| 5 | Тема письма из названия компании | Инъекция заголовков письма | Очистка переводов строк |
| 6 | Цена в корзине не сверялась с БД при оформлении | Заказ по устаревшей цене после правки админом/1С | Сверка цены и упаковки, клиенту показывается актуальная цена |
| 7 | Блокировка строк в произвольном порядке | Взаимные блокировки (deadlock) при одновременных заказах | Единый порядок `ORDER BY id` |
| 8 | Для позиций из предзаказа не проверялся физический остаток | Заказ больше, чем есть на складе | Добавлена проверка |
| 9 | `async def` + синхронная БД, Excel и PDF в основном потоке | Один тяжёлый запрос тормозит сайт для всех | Обычные `def` (пул потоков), Excel-разбор в потоке |
| 10 | Пул БД 10+20 на воркер | При нескольких воркерах упирались бы в `max_connections` | Настраиваемый пул, согласован с PostgreSQL |
| 11 | 1С: нет лимита на Basic Auth, нет проверки значений | Перебор пароля; мусор в базе из выгрузки | Лимит запросов, потолок 20 000 товаров, проверка цены/остатка |
| 12 | Нет шрифтов для PDF в репозитории; CSP блокировал карту; lock-файлы в `/run` | Квадраты в счетах; нет карты; падение в контейнере | Исправлено в Docker-комплекте и `middleware.py` |
| 13 | Неверный путь к `static` в PDF | Логотип/шрифты в счёте не находились | Исправлен |

## Что осталось на будущее (по убыванию пользы)

1. **Миграции через Alembic.** Сейчас схема правится самописным `auto_migrate` (добавляет колонки/индексы).
   Для переименований и изменения типов нужен Alembic (в проекте он уже подключён, но без версий).
2. **Фоновые письма** отправляются из процесса приложения (`BackgroundTasks`). При росте нагрузки лучше вынести
   в очередь (RQ/Celery поверх уже имеющегося Redis).
3. **Поиск `ILIKE '%…%'`** по каталогу не использует индексы; при десятках тысяч товаров — `pg_trgm`.
4. **Метрики и алерты** (Sentry уже подключается; добавить внешний монитор доступности).
5. **Покрытие тестами**: добавить тесты оформления заказа (гонки, цена/остаток) и обмена с 1С.
6. Два одновременных запроса одного пользователя (например, быстрые клики «в корзину») могут перезаписать
   друг друга в сессии (последняя запись побеждает). Лечится атомарной корзиной в Redis/БД.
