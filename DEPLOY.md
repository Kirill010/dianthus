# 🚚 Перенос работающего сайта на новый сервер

Этот файл — для случая, когда сайт **уже работает** на старом сервере и его нужно
перевезти (на новый VPS, в Docker) **с сохранением базы, клиентов, заказов и фото**.

* Ставите сайт **с нуля** (нет ни сервера, ни домена, ни данных)? Вам нужен другой
  документ: **[docs/GUIDE_FROM_SCRATCH.md](docs/GUIDE_FROM_SCRATCH.md)**.
* Обмен с 1С: **[docs/1C_INTEGRATION.md](docs/1C_INTEGRATION.md)**.

Порядок: подготовить новый сервер → перевезти данные (пробно) → переключить DNS →
включить HTTPS → проверить → держать старый сервер в запасе.

> **Старый сервер не трогаем** до самого переключения домена — на нём остаются
> рабочий сайт и откат.

---

## 1. Подготовьте новый сервер

Выполните разделы **4–11** руководства
[docs/GUIDE_FROM_SCRATCH.md](docs/GUIDE_FROM_SCRATCH.md) (покупка VPS → SSH → настройка
сервера → код → `.env` → первый запуск) — **кроме** пунктов про DNS и HTTPS: домен пока
указывает на старый сервер, поэтому HTTPS на новом сервере вы включите уже после
переключения (раздел 4 ниже).

Итог этого шага: на новом сервере `docker compose ps` показывает все сервисы
`Up (healthy)`, а `curl -s -o /dev/null -w "%{http_code}\n" -H "Host: dianthus-opt.ru" http://127.0.0.1/login`
отвечает `200`. Сайт при этом пока **пустой** (чистая база).

> ⚠️ После переезда все клиенты **один раз войдут заново**, а неоформленные корзины
> пропадут (сессии лежат в Redis нового сервера). Предупредите клиентов заранее
> и переносите данные в нерабочее время.

---

## 2. Перенос данных

База и фото живут отдельно от кода — переносим вручную.

> **Рекомендация: два прогона.** Сначала **пробный** (старый сайт продолжает
> работать, вы проверяете, что всё переносится). Потом **финальный** — в «окно
> обслуживания» (ночью), чтобы не потерять заказы между выгрузкой и переключением.

### 2.1. На старом сервере — сделать выгрузки

```bash
ssh root@СТАРЫЙ_IP
```

```bash
sudo -u postgres pg_dump --no-owner --no-acl --clean --if-exists dianthus | gzip > /tmp/dianthus_db.sql.gz
tar -czf /tmp/dianthus_uploads.tar.gz -C /var/www/dianthus/app/static/uploads .
ls -lh /tmp/dianthus_*
psql --version
```

Оба файла должны быть ненулевого размера. `-C … .` важно: фото окажутся в корне
архива. Новая база — PostgreSQL **16**; дамп из версии ≤ 16 загрузится без проблем.
(Если у вас 17+ — загрузка может потребовать правки; напишите.)

Пути `dianthus` (имя базы) и `/var/www/dianthus/...` приведены для типичной
установки; если у вас иначе — подставьте свои.

### 2.2. На новом сервере — забрать файлы

```bash
cd ~
scp root@СТАРЫЙ_IP:/tmp/dianthus_db.sql.gz .
scp root@СТАРЫЙ_IP:/tmp/dianthus_uploads.tar.gz .
```

(пароль/ключ — от **старого** сервера)

### 2.3. Восстановить базу (приложение пока остановлено)

```bash
cd /opt/dianthus
docker compose build
bash scripts/restore-db.sh ~/dianthus_db.sql.gz
```

Введите `yes`. В конце скрипт покажет число пользователей, товаров и заказов —
**сверьте со старым сайтом**.

### 2.4. Запустить всё и восстановить фото

```bash
docker compose up -d
bash scripts/restore-uploads.sh ~/dianthus_uploads.tar.gz
```

Проверка: `docker compose ps` (все `healthy`), `docker compose logs app --tail=40`
(нет `Traceback`). Приложение само доведёт схему базы до актуальной: при старте
выполняется **авто-миграция** (добавляются новые колонки и индексы, данные не
затрагиваются; это проверено на базе, созданной старой версией кода).

### 2.5. Финальный прогон (ночью, перед переключением DNS)

1. На **старом** сервере остановите приложение (например,
   `sudo systemctl stop dianthus`; точное имя — `systemctl list-units | grep -i dianthus`).
   С этого момента старый сайт недоступен — заказы не принимаются.
2. Снова выполните 2.1 → 2.2.
3. На новом: `bash scripts/restore-db.sh ~/dianthus_db.sql.gz`, затем `docker compose up -d`
   и `bash scripts/restore-uploads.sh ~/dianthus_uploads.tar.gz`.
4. Сразу переходите к разделу 3.

## 3. Переключение домена (DNS)

**За 1–2 суток до переноса** в DNS домена уменьшите TTL записей до **300** секунд —
тогда переключение и откат займут минуты, а не часы.

В день переноса, после финального прогона (2.5):

1. Панель DNS → A-записи для `@` (dianthus-opt.ru) и `www`.
2. Замените IP на **новый**. Сохраните. Убедитесь, что **нет записей `AAAA`**.
3. Проверка (ваш компьютер или сервер):

```bash
dig +short dianthus-opt.ru
dig +short www.dianthus-opt.ru
```

(Windows: `nslookup dianthus-opt.ru`.) Оба должны вернуть **новый IP**. Обычно 5–30 минут.

---

## 4. HTTPS на новом сервере

Как только DNS показывает новый IP — **сразу** (пока не включён HTTPS, вход на сайт
не работает):

```bash
cd /opt/dianthus
bash scripts/init-ssl.sh admin@dianthus-opt.ru
```

Ожидаемый финал: `✅ HTTPS включён: https://dianthus-opt.ru`. Подробности и разбор
ошибок — в [GUIDE_FROM_SCRATCH.md, раздел 11](docs/GUIDE_FROM_SCRATCH.md#11-https).

## 5. Проверка после переезда

- [ ] https://dianthus-opt.ru открывается с замком; `www.` перенаправляет на основной адрес
- [ ] Вход админом работает; каталог и фото товаров отображаются
- [ ] «Контакты»: карта Яндекса показывается
- [ ] Оформление тестового заказа проходит; в админке он виден; **время заказа — по
      Москве**, а не на 3 часа раньше
- [ ] PDF-счёт скачивается, в нём **кириллица**, а не квадраты
- [ ] Приходят письма (заявка, заказ) на адреса из `SMTP_TO`; клиенту уходит письмо о принятом заказе
- [ ] Неверный пароль 3 раза подряд → блокировка (защита работает)
- [ ] Поиск по каталогу находит «роза» и «Роза» (иначе см. GUIDE, раздел 10, проверка локали)
- [ ] `docker compose logs app --tail=50` — без `ERROR`/`Traceback`
- [ ] Заголовки безопасности:
      `curl -sI https://dianthus-opt.ru/login | grep -iE "strict-transport|content-security|x-frame"`
- [ ] Обмен с 1С: `python scripts/onec_smoke_test.py https://dianthus-opt.ru 1c_dianthus ПАРОЛЬ`
- [ ] Включена 2FA у администратора; `ADMIN_PASSWORD` убран из `.env`
- [ ] Настроены резервные копии (cron) и копия **вне сервера** — раздел 15 гайда

---

## 6. Откат переключения

Верните в DNS **старый IP** (при TTL 300 — через ~5 минут всё вернётся). Старый
сервер держите включённым ещё 3–5 дней после переноса. Если на новом сервере уже
появились заказы, перед откатом сделайте `bash scripts/backup.sh`, чтобы не
потерять их (потом перенесите эти заказы вручную или повторите перенос данных
в обратную сторону).
