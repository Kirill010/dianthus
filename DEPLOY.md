# 🚀 Диантус: перенос на новый VPS и запуск в Docker

Пошаговая инструкция «с нуля» для сервера Reg.ru (Ubuntu 24.04) и домена `dianthus-opt.ru`.
Все команды копируйте по одной. Если на любом шаге вывод отличается от ожидаемого —
остановитесь и пришлите вывод, не продолжайте.

---

## 0. Что это и зачем

**Docker** упаковывает каждую часть сайта в отдельный изолированный «контейнер» вместе со всем,
что ей нужно. Сервер собирается из файлов-рецептов (`Dockerfile`, `docker-compose.yml`), а не из
десятка ручных установок. Поэтому:

- новый сервер = 3 команды, а не «весь вечер»;
- обновление = одна команда (`./scripts/update.sh`);
- сбой или взлом одного контейнера не открывает автоматически весь сервер;
- сервер одинаков на тесте и в проде.

Docker **не заменяет SSH**: к VPS вы по-прежнему подключаетесь по SSH, но дальше запускаете готовые скрипты.

### Что будет работать на сервере

```
Интернет ──► :80/:443 ──► [nginx] ──► [app: FastAPI, WEB_CONCURRENCY воркеров] ──► [db: PostgreSQL 16]
                │                              │
                │                              └──────────────────► [redis: лимиты, блокировки входа]
                └─ фото товаров отдаёт сам nginx          [certbot: продление HTTPS-сертификата]
```

Наружу открыты **только** порты 22 (SSH), 80 и 443. База и Redis снаружи недоступны.

### Что изменено в проекте (кроме Docker)

| Файл | Что и зачем |
|---|---|
| `app/session.py` (новый), `app/main.py`, `app/auth.py` | **Серверные сессии в Redis.** Раньше вся сессия лежала в cookie (лимит браузера ≈ 4 КБ): корзина из 10–15 позиций не помещалась, и клиента «выкидывало» из аккаунта. Теперь в cookie только подписанный идентификатор. При входе/выходе выдаётся новый идентификатор (защита от фиксации сессии) |
| `app/config.py` | В `prod` без валидного `SECRET_KEY` приложение **не стартует** (раньше каждый воркер генерировал свой ключ, и сессии «ломались» между воркерами) |
| `app/routers/*.py` | Обработчики с обращением к БД переведены на обычные `def` — FastAPI запускает их в пуле потоков, и один тяжёлый запрос (Excel, PDF, большой каталог) больше не «замораживает» сайт для всех. Разбор Excel вынесен в поток |
| `app/routers/cart.py` | При оформлении заказа цена и размер упаковки сверяются с БД (цену мог изменить админ или 1С, пока товар лежал в корзине): клиент видит актуальную цену, а не оформляет по старой. Проверка физического остатка для позиций из предзаказа. Одинаковый порядок блокировки строк — нет взаимных блокировок (deadlock) |
| `app/routers/integration_1c.py` | Лимит запросов с IP (защита Basic Auth от перебора), не более 20 000 товаров за обмен, мусорные значения цены/остатка отбрасываются, а не портят базу |
| `app/services/pdf_*.py`, `notifier.py`, `scheduler.py` | Весь пользовательский текст в PDF-счетах и письмах экранируется (иначе — HTML-инъекция в письмо админу и чтение файлов/запросы наружу через PDF-генератор). Тема письма — без переводов строк. Исправлен путь к папке `static` для картинок в PDF |
| `app/database.py` | Размер пула соединений на воркер настраивается (`DB_POOL_SIZE`, `DB_MAX_OVERFLOW`) и согласован с лимитом PostgreSQL |
| `app/middleware.py` | В CSP добавлен `frame-src` для Яндекс-карты |
| `app/locks.py` (новый), `app/migrations.py`, `app/scheduler.py` | **Блокировка файлов теперь кроссплатформенная.** Было `import fcntl` — модуль есть только в Linux, поэтому на Windows приложение вообще не запускалось (`ModuleNotFoundError: No module named 'fcntl'`), и тесты падали на этапе сбора. Теперь fcntl на Linux/macOS, `msvcrt` на Windows, при отсутствии обоих — работа без блокировки с предупреждением |
| `nginx/nginx.conf`, `nginx/site_*.conf` | **Исправлены лимиты запросов.** Раньше жёсткий лимит `10 запросов/мин` стоял на ЛЮБОЙ POST: оптовый клиент, быстро добавляющий товары в корзину, получал «429 Слишком много запросов». Теперь 10r/m — только на отправку форм входа и регистрации, остальные POST — 120r/m (burst 30) |
| `app/routers/admin.py`, `app/scheduler.py` | **Защита служебной поставки 1С.** Разгрузка/снятие/удаление такой поставки вручную деактивировало ВСЕ позиции каталога (в ней лежат текущие остатки от 1С). Теперь эти действия для неё запрещены на уровне админки и самого `do_unload` |
| `app/routers/profile.py` | При смене пароля выдаётся новый идентификатор сессии (перехваченный старый перестаёт работать) |
| `app/routers/catalog.py`, `app/services/upload_service.py`, `app/routers/admin.py`, `app/main.py` | Мелочи: ограничение длины поискового запроса (100 символов), вместо `print()` в загрузке фото — лог, `datetime.utcnow()` заменён на `datetime.now(timezone.utc)` (в Python 3.12+ первый помечен устаревшим) |
| `requirements.txt` | Удалён неиспользуемый `slowapi` (лимиты реализованы в `app/security.py`) |
| `tests/test_session.py` | Тест серверных сессий |
| Docker, nginx, `scripts/*.sh` | Сборка, прокси, HTTPS, бэкапы, обновление |

Особенности вашего кода, которые Docker-комплект учитывает автоматически:

1. **Шрифтов для PDF в репозитории нет** → в счетах была бы «каша» вместо кириллицы. Образ ставит DejaVu и кладёт в `app/static/fonts`.
2. **Lock-файлы** миграций и планировщика пишутся в `/run/dianthus`, недоступный обычному пользователю → в compose заданы пути в `/tmp/dianthus`.
3. **Cookie сессии только по HTTPS** (`ENV=prod`) → войти на сайт можно только после шага 10 (SSL).
4. **Сессии хранятся в Redis** (том не нужен: у Redis отключена запись на диск, `--save ""`).
   Перезапуск **приложения** сессии не сбрасывает; перезапуск контейнера `redis` — сбрасывает.
   **После переезда на новый сервер все клиенты один раз войдут заново**, а неоформленные корзины
   пропадут — предупредите клиентов заранее (и переносите данные в нерабочее время).

## 1. Какой тариф VPS брать (4 ГБ или 6 ГБ)

Для вашей задачи (B2B-каталог, обмен с 1С, десятки–сотни клиентов) хватает и младшего тарифа;
на 6 ядрах — с запасом. **Значения по умолчанию в `docker-compose.yml` рассчитаны на тариф
4 ядра / 4 ГБ** (например, DDC C4-M4-D80), чтобы ничего не падало от нехватки памяти:

| Сервис | Лимит памяти (по умолчанию) | Настройки |
|---|---|---|
| PostgreSQL 16 | 1 ГБ | `shared_buffers=256MB`, `work_mem=8MB`, `max_connections=100` |
| Приложение | 1,5 ГБ | `WEB_CONCURRENCY` = 2 воркера (переменная окружения), пул БД 6+9 соединений на воркер (до 30 всего) |
| Redis | 256 МБ | `maxmemory 128MB`, без записи на диск (`--save ""`; сессии живут в памяти) |
| nginx + certbot | по 128 МБ | — |

**Если у вас тариф на 6 ядер / 6 ГБ** (HP C6-M6-D100 и подобные) — поднимите лимиты так:

```bash
cd /opt/dianthus
# в .env добавьте строку:
#   WEB_CONCURRENCY=4
# затем в docker-compose.yml замените mem_limit у db на 2g, у app на 2560m,
# а в command у db — shared_buffers=512MB и work_mem=16MB, затем:
docker compose up -d
```

Остальное — операционная система и файловый кэш; на всякий случай создаётся swap 4 ГБ.
`DB_POOL_SIZE × (воркеры)` не должно превышать `max_connections` PostgreSQL.

Первую неделю смотрите `docker stats --no-stream` и `free -h`. Если память стабильно >85% или swap активно растёт —
уменьшите `WEB_CONCURRENCY` до 1–2 или перейдите на тариф с 8 ГБ.

> Диск 100 ГБ: ~15 ГБ — система и Docker-образы, остальное — база, фото и бэкапы (14 дней).
> Следите за `df -h`; сильно разросшиеся фото/бэкапы переносите во внешнее хранилище.

## 2. Покупка VPS

1. Reg.ru → «Облачные серверы / VPS» → создать.
2. ОС: **Ubuntu 24.04 LTS** (не 22.04 и не 25.x). Тариф — на выбор:
   - **4 ядра / 4 ГБ / 80 ГБ** (DDC C4-M4-D80 и подобные) — минимум, работает «как есть», ничего менять не нужно;
   - **6 ядер / 6 ГБ / 100 ГБ** (HP C6-M6-D100) — комфортно; после установки поднимите лимиты (шаг 1).
3. Если панель предлагает добавить **SSH-ключ** — добавьте (см. шаг 3). Если нет — будет пароль root.
4. Запишите **IP нового сервера** и пароль (в менеджер паролей).

Старый сервер **не трогаем** до самого переключения.

## 3. SSH-ключ (вход без пароля) и первое подключение

SSH-ключ — это пара файлов: «замок» (публичный ключ, лежит на сервере) и «ключ от замка»
(приватный, только у вас). Подобрать его перебором нельзя.

**На вашем компьютере** (Windows: PowerShell; Mac/Linux: Терминал):

```bash
ssh-keygen -t ed25519 -C "dianthus"
```
На все вопросы нажмите Enter (лучше задать парольную фразу). Затем покажите публичный ключ:

```bash
# Windows PowerShell
type $env:USERPROFILE\.ssh\id_ed25519.pub
# Mac / Linux
cat ~/.ssh/id_ed25519.pub
```

Подключитесь к серверу (замените IP):

```bash
ssh root@НОВЫЙ_IP
```
На вопрос `Are you sure you want to continue connecting` ответьте `yes`, введите пароль root.
Вы увидите приглашение вида `root@...:~#`.

Добавьте свой публичный ключ на сервер (вставьте вашу строку `ssh-ed25519 AAAA...` целиком):

```bash
mkdir -p ~/.ssh && chmod 700 ~/.ssh
echo 'ssh-ed25519 AAAA...ВАШ_КЛЮЧ... dianthus' >> ~/.ssh/authorized_keys
chmod 600 ~/.ssh/authorized_keys
```

## 4. Настройка сервера одной командой

Сначала скопируйте два скрипта из архива проекта на сервер. **На вашем компьютере**, в папке проекта:

```bash
scp scripts/server-setup.sh scripts/harden-ssh.sh root@НОВЫЙ_IP:/root/
```

Затем **на сервере** под `root`:

```bash
bash /root/server-setup.sh
```

Скрипт: обновит систему, включит автообновления безопасности, создаст пользователя `deploy`,
поставит Docker, включит файрвол (22/80/443), `fail2ban` против подбора SSH и swap 4 ГБ.
В конце он покажет версии Docker/Compose и статус файрвола.

### 4.1. Проверьте вход под `deploy` — в НОВОМ окне терминала

```bash
ssh deploy@НОВЫЙ_IP
```
Должны войти **без пароля** (по ключу). Только после этого — в этом же окне `deploy`:

```bash
sudo bash /root/harden-ssh.sh
```
Он отключит вход по паролю и вход под `root`. Затем **снова проверьте** новое подключение
`ssh deploy@НОВЫЙ_IP`, прежде чем закрывать старые окна.

> Если вход под `deploy` не получился — НЕ запускайте `harden-ssh.sh`. Пришлите вывод ошибки.

## 5. Положить проект на сервер

### Вариант A (рекомендуется): через GitHub

На **вашем компьютере**: распакуйте архив `dianthus-deploy.tar.gz` поверх папки вашего локального
репозитория (файлы заменятся/добавятся), затем:

```bash
git status                 # убедитесь, что в списке НЕТ .env и бэкапов
git add -A
git commit -m "Docker-деплой: Dockerfile, compose, nginx, скрипты"
git push
```

На **сервере** (под `deploy`):

```bash
sudo mkdir -p /opt/dianthus && sudo chown deploy:deploy /opt/dianthus
git clone https://github.com/Kirill010/dianthus.git /opt/dianthus
cd /opt/dianthus && ls
```
Должны быть: `Dockerfile`, `docker-compose.yml`, `nginx/`, `scripts/`, `app/`.

Если вы готовили файлы на Windows, права на запуск скриптов могли потеряться — выдайте их:
```bash
chmod +x scripts/*.sh
```

### Вариант B: без GitHub (копирование архива)

С вашего компьютера:
```bash
scp dianthus-deploy.tar.gz deploy@НОВЫЙ_IP:/tmp/
```
На сервере:
```bash
sudo mkdir -p /opt/dianthus && sudo chown deploy:deploy /opt/dianthus
tar xzf /tmp/dianthus-deploy.tar.gz -C /opt/dianthus && cd /opt/dianthus
```
(Тогда `update.sh` через `git pull` работать не будет — придётся заливать архив заново.)

## 6. Настройка `.env` (пароли)

```bash
cd /opt/dianthus
./scripts/prepare.sh dianthus-opt.ru admin@dianthus-opt.ru
```
Вместо `admin@dianthus-opt.ru` укажите **реальный** email админа. Скрипт сгенерирует случайные
пароли БД, Redis, секретный ключ, пароль админа и пароль для 1С, и **один раз покажет** пароль админа
и 1С — запишите их в менеджер паролей.

Теперь заполните почту:

```bash
nano .env
```
Заполните `SMTP_USER`, `SMTP_PASSWORD`, `SMTP_FROM`, `SMTP_TO`.
Для Яндекс.Почты нужен **«пароль приложения»** (Яндекс ID → Безопасность → Пароли приложений),
а не пароль от ящика. Сохранить: `Ctrl+O`, `Enter`, `Ctrl+X`.

> 🔐 Пароли из прежней инструкции (`Dianthus-Opt!2026#Secure` и т.п.) были опубликованы —
> нигде их не используйте. Если вы когда-либо коммитили `.env` в GitHub, смените **все** пароли
> (в т.ч. почты) и считайте старые скомпрометированными.

## 7. Первый запуск

```bash
cd /opt/dianthus
docker compose build
```
Первая сборка занимает 3–6 минут. В конце должно быть `Image dianthus-app:latest Built` без `ERROR`.

> Если сборка упала — пришлите последние 30 строк вывода. Я не мог собрать образ у себя
> (в моей среде закрыт доступ к PyPI), поэтому первая сборка — это настоящая проверка.

Дальше **не запускайте всё сразу, если переносите данные** (шаг 8): сначала поднимается только база.

- **Если сайт новый и пустой** — просто: `docker compose up -d`
- **Если переносите данные со старого сервера** — перейдите к шагу 8, там порядок другой.

Проверка:

```bash
docker compose ps
```
Все сервисы `Up`, у `db`, `redis`, `app` статус `(healthy)`.

```bash
docker compose logs app --tail=40
```
Ищите строку `🌸 Диантус готов (prod)` и отсутствие `ERROR`/`Traceback`.

Проверка ответа сайта (с самого сервера, домен подставляется заголовком):

```bash
curl -s -o /dev/null -w "%{http_code}\n" -H "Host: dianthus-opt.ru" http://127.0.0.1/login
```
Ожидается `200`.

> Войти в админку по `http://IP` не получится — это защита: cookie сессии работает только по HTTPS.
> Пробный вход возможен через SSH-туннель (в Chrome/Edge `localhost` считается безопасным адресом).
> На вашем компьютере: `ssh -L 8080:127.0.0.1:80 deploy@НОВЫЙ_IP`, затем откройте
> `http://localhost:8080`. Если не заработает — не страшно, проверите после шага 10.

## 8. Перенос данных со старого сервера

База и фото живут отдельно от кода — их переносим вручную.

> **Рекомендация: два прогона.** Сначала пробный (сайт старого сервера продолжает работать,
> вы проверяете, что всё переносится). Потом финальный в «окно обслуживания» (ночью), чтобы не потерять
> заказы, сделанные между дампом и переключением.

### 8.1. На старом сервере — сделать выгрузки

```bash
ssh root@СТАРЫЙ_IP
```
```bash
sudo -u postgres pg_dump --no-owner --no-acl --clean --if-exists dianthus | gzip > /tmp/dianthus_db.sql.gz
tar -czf /tmp/dianthus_uploads.tar.gz -C /var/www/dianthus/app/static/uploads .
ls -lh /tmp/dianthus_*
psql --version
```
Два файла должны быть ненулевого размера. `-C ... .` важно: фото окажутся в корне архива.
Запомните версию `psql`: новая БД — PostgreSQL **16**. Дамп из версии ≤16 загрузится без проблем;
если у вас 17+, напишите мне.

### 8.2. На новом сервере — забрать файлы

```bash
cd ~
scp root@СТАРЫЙ_IP:/tmp/dianthus_db.sql.gz .
scp root@СТАРЫЙ_IP:/tmp/dianthus_uploads.tar.gz .
```
(пароль — от **старого** сервера)

### 8.3. Восстановить базу (приложение пока не запущено)

```bash
cd /opt/dianthus
docker compose build
./scripts/restore-db.sh ~/dianthus_db.sql.gz
```
Введите `yes`. В конце скрипт покажет число пользователей, товаров и заказов — сверьте со старым сайтом.

### 8.4. Запустить всё и восстановить фото

```bash
docker compose up -d
./scripts/restore-uploads.sh ~/dianthus_uploads.tar.gz
```
Проверка: `docker compose ps` (все `healthy`), `docker compose logs app --tail=40` (нет `Traceback`).
Приложение само доведёт схему БД до актуальной (авто-миграция при старте).

### 8.5. Финальный прогон (ночью, перед переключением DNS)

1. На **старом** сервере остановите приложение (у вас это, вероятно, systemd-служба,
   например `sudo systemctl stop dianthus`; точное имя — `systemctl list-units | grep -i dianthus`).
   С этого момента старый сайт недоступен — заказы не принимаются.
2. Снова выполните шаги 8.1 → 8.2 (новые файлы заменят старые).
3. На новом: `./scripts/restore-db.sh ~/dianthus_db.sql.gz`, затем `docker compose up -d`,
   `./scripts/restore-uploads.sh ~/dianthus_uploads.tar.gz`.
4. Сразу переходите к шагу 9.

## 9. Переключение домена (DNS)

**За 1–2 суток до переноса** в DNS-настройках домена уменьшите TTL записей до 300 секунд —
тогда переключение и откат займут минуты, а не часы.

В день переноса, после финального прогона (8.5):

1. Панель DNS → найдите A-записи для `@` (dianthus-opt.ru) и `www`.
2. Замените IP на **новый**. Сохраните.
3. Проверка (с вашего компьютера или сервера):

```bash
dig +short dianthus-opt.ru
dig +short www.dianthus-opt.ru
```
Оба должны вернуть **новый IP**. Обычно 5–30 минут.

## 10. HTTPS (SSL-сертификат)

Как только `dig` показывает новый IP — **сразу** (до этого момента логин на сайте не работает):

```bash
cd /opt/dianthus
./scripts/init-ssl.sh admin@dianthus-opt.ru
```
Скрипт проверит DNS, получит бесплатный сертификат Let's Encrypt и включит HTTPS-конфиг nginx
(с автоматическим откатом на HTTP, если конфиг окажется неверным).
Ожидаемый финал: `✅ HTTPS включён: https://dianthus-opt.ru`.
Сертификат продлевается сам (контейнер `certbot`).

Откройте https://dianthus-opt.ru — должен быть замок, а `http://` должен перенаправлять на `https://`.

### Обмен с 1С

Авторизация — HTTP Basic: логин `INTEGRATION_USER`, пароль `INTEGRATION_PASSWORD` из `.env`
(эти же логин и пароль вводятся в 1С). Проверка связи:

```bash
curl -u 1c_dianthus:ПАРОЛЬ https://dianthus-opt.ru/api/1c/ping
```

| Метод | Адрес | Направление |
|---|---|---|
| `POST` | `/api/1c/products/sync` | 1С → сайт: каталог, цены, остатки (до 20 000 позиций за раз) |
| `GET` | `/api/1c/products/export` — только товары «на полке»; `?all=1` — весь справочник | сайт → 1С |
| `GET` | `/api/1c/orders/export?since=2026-02-01T00:00:00&status=Новый&limit=200` | сайт → 1С: заказы |
| `GET` | `/api/1c/ping` | проверка связи |

**Формат товара — одинаковый в обе стороны:**

```json
{
  "products": [
    {
      "id": 1,
      "external_id": "ROSA-FREEDOM-60",
      "sku": "ROSA-FREEDOM-60",
      "name": "Роза Freedom 60 см",
      "description": "Классическая красная роза",
      "country": "Эквадор",
      "length_cm": 60,
      "unit": "упаковка",
      "package_size": 25,
      "min_quantity": 1,
      "category": "Роза Эквадор",
      "price_per_stem": 42.50,
      "stock_packs": 120,
      "photos": ["https://dianthus-opt.ru/static/uploads/abc.webp"]
    }
  ]
}
```

Смысл полей — не перепутайте, иначе цены разъедутся в 25 раз:

| Поле | Значение |
|---|---|
| `id` (в запросе из 1С) | идентификатор товара **в 1С** (код или GUID). Сохраняется в товаре и используется для сопоставления |
| `id` (в ответе сайта) | идентификатор товара **на сайте** |
| `external_id` | идентификатор товара в 1С — то, что 1С присылает в `id` |
| `price_per_stem` | цена за **штуку (стебель)**, не за упаковку |
| `stock_packs` | остаток в **упаковках**, не в штуках |
| `package_size` | сколько штук в упаковке (25 для розы) |
| `min_quantity` | минимальный заказ в упаковках |

Порядок сопоставления товара при синхронизации: `id` из 1С (`external_id`) → `sku` → название.
Благодаря этому переименование номенклатуры в 1С не создаёт дубль. У товаров, заведённых
раньше, `external_id` автоматически заполняется значением `sku` (разовая миграция при старте).

**Заказы для 1С** (`/api/1c/orders/export`) отдаются блоками по возрастанию `id`:

```json
{
  "count": 1,
  "orders": [
    {
      "id": 57,
      "number": "САЙТ-57",
      "created_at": "2026-02-14T09:31:00",
      "status": "Новый",
      "comment": "Позвонить за час",
      "subtotal": 2125.0,
      "discount_percent": 0,
      "total": 2125.0,
      "buyer": {"company": "ООО Ромашка", "contact": "Иван Иванов",
                "inn": "7701234567", "phone": "+79001234567",
                "email": "shop@test.ru", "city": "Москва"},
      "items": [
        {"sku": "ROSA-FREEDOM-60", "name": "Роза Freedom 60 см",
         "quantity_packs": 2, "package_size": 25, "stems": 50,
         "price_per_stem": 42.5, "sum": 2125.0}
      ]
    }
  ]
}
```

Идемпотентность: 1С ищет документ по номеру `САЙТ-<id>` и обновляет его, а не создаёт новый —
повторный вызов с тем же `since` безопасен. `since` — время последней успешной выгрузки
(ISO 8601); `status` — фильтр по статусу сайта; `limit` — не больше 200 за раз.

Пример вызова из 1С (регламентное задание, каждые 15 минут):

```bsl
Пароль = "<пароль из .env>";
Соединение = Новый HTTPСоединение(
    "dianthus-opt.ru", 443, "1c_dianthus", Пароль, , 60,
    Новый ЗащищенноеСоединениеOpenSSL());

Запрос = Новый HTTPЗапрос("/api/1c/orders/export?since=" + ПоследняяВыгрузка());
Ответ = Соединение.ВызватьHTTPМетод("GET", Запрос);
Если Ответ.КодСостояния = 200 Тогда
    Данные = ПрочитатьJSON(Новый ЧтениеJSON, Ответ.ПолучитьТелоКакСтроку());
    Для Каждого ЗаказJSON Из Данные.orders Цикл
        // создать/обновить «Заказ клиента» с Номером = ЗаказJSON.number
    КонецЦикла;
КонецЕсли;
```

Если сертификат Let's Encrypt не проходит проверку на сервере 1С — установите туда корневой
сертификат **ISRG Root X1** в хранилище «Доверенные корневые центры».

Дополнительная защита: в `nginx/site-https.conf` в блоке `location /api/1c/` раскомментируйте
`allow <IP вашего сервера 1С>; deny all;` — тогда в обмен смогут попасть только с этого адреса.
Применить: `sed "s/__DOMAIN__/dianthus-opt.ru/g" nginx/site-https.conf > nginx/conf.d/site.conf && docker compose exec nginx nginx -t && docker compose exec nginx nginx -s reload`.

Для больших выгрузок лимит тела запроса 50 МБ, таймаут 5 минут. Если 1С шлёт больше — увеличьте
`client_max_body_size` в этом же блоке.

## 12. Резервные копии (обязательно!)

```bash
cd /opt/dianthus
./scripts/backup.sh
ls -lh backups/
```
Создаются `db-*.sql.gz` (база) и `uploads-*.tar.gz` (фото); хранятся 14 дней.

Автозапуск каждую ночь в 03:15:

```bash
crontab -e
```
(выберите `nano`, если спросит) и добавьте строку в конец:

```
15 3 * * * cd /opt/dianthus && ./scripts/backup.sh >> /opt/dianthus/backups/backup.log 2>&1
```

**Копии на том же сервере не спасут, если сервер потеряется.** Раз в неделю копируйте `backups/`
на свой компьютер или во внешнее хранилище (S3 у Reg.ru, Яндекс Object Storage, другой сервер):

```bash
# с вашего компьютера
scp -r deploy@НОВЫЙ_IP:/opt/dianthus/backups ./dianthus-backups
```

**Проверьте, что бэкап восстанавливается** (хотя бы один раз): скачайте дамп и выполните
`./scripts/restore-db.sh backups/db-....sql.gz` на тестовом сервере.

Восстановление из бэкапа (аварийное):
```bash
./scripts/restore-db.sh backups/db-ГГГГММДД-ЧЧММСС.sql.gz
docker compose up -d
./scripts/restore-uploads.sh backups/uploads-ГГГГММДД-ЧЧММСС.tar.gz
```

## 13. Повседневная работа

| Действие | Команда (в `/opt/dianthus`) |
|---|---|
| Обновить сайт из GitHub (с бэкапом) | `./scripts/update.sh` |
| Состояние контейнеров | `docker compose ps` |
| Логи приложения (живые) | `docker compose logs -f app` |
| Логи nginx | `docker compose logs --tail=100 nginx` |
| Перезапустить приложение | `docker compose restart app` |

### Откат переключения (если что-то пошло не так)
Верните в DNS старый IP (при TTL 300 — через ~5 минут всё вернётся). Старый сервер держите
включённым ещё 3–5 дней после переноса. Если после переключения на новом сервере уже появились заказы,
перед откатом сделайте `./scripts/backup.sh`, чтобы не потерять их.

## 14. Решение проблем

**`docker compose ps` — `app` в `unhealthy` / перезапускается**
`docker compose logs app --tail=80`. Типичные причины: опечатка в `.env`; `DATABASE_URL` не совпал
с `POSTGRES_PASSWORD`; БД ещё не готова (подождите минуту).

**Не могу войти в сайт, пишет «Ошибка CSRF-токена» / ничего не происходит**
Вы открыли сайт по `http://` или по IP. Заходите на `https://dianthus-opt.ru` (шаг 10).

**Все получают «Слишком много запросов» (429)**
Лимиты в `nginx/nginx.conf`: `zone=auth` (10 запросов/мин) — только на отправку форм
входа и регистрации; `zone=posts` (120/мин) — на остальные POST; `zone=general` (20/с) — на всё.
Проверьте логи, не идёт ли один IP на сайт слишком часто (например, внутренний монитор).
Лимит можно поднять и выполнить `docker compose exec nginx nginx -s reload`.
Если 429 получают живые клиенты при работе с корзиной — поднимите `rate` в `zone=posts`.

**`init-ssl.sh`: «challenge failed»**
DNS ещё не обновился (`dig +short dianthus-opt.ru` должен показывать новый IP), либо порт 80 закрыт.
Подождите и повторите. Let's Encrypt ограничивает число неудачных попыток — не запускайте скрипт чаще 5 раз в час.

**Фото товаров не видны**
`./scripts/restore-uploads.sh ...` не выполнен или в архиве лишний уровень папок. Проверка:
`docker compose exec app ls /app/app/static/uploads | head`.

**PDF-счёт: квадраты вместо букв**
`docker compose exec app ls /app/app/static/fonts` — должны быть два файла DejaVu. Если нет — пересоберите образ:
`docker compose build --no-cache app && docker compose up -d`.

**Заканчивается диск**
`docker system df`, затем `docker image prune -f` и очистка старых файлов в `backups/`.
