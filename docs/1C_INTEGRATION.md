# Обмен сайта с 1С

Руководство для владельца и для разработчика сайта: как устроен обмен и что с ним делать.
Сайт предоставляет HTTP-API (`/api/1c/...`), 1С по расписанию **сама ходит на сайт**: присылает
инвойсы (поставки), забирает заказы и сообщает статусы. Сайт к 1С не обращается — поэтому не нужно
открывать доступ к серверу 1С из интернета.

**Форматы, примеры запросов и кода 1С — не здесь, а в двух файлах для программиста** (они же открыты
на сайте без входа): памятка [`1C_PROGRAMMER_BRIEF.md`](1C_PROGRAMMER_BRIEF.md) (`/1c-docs`) и все форматы
одним файлом [`1C_FORMATS.json`](1C_FORMATS.json) (`/1c-docs.json`). Исходники лежат в `app/content/`,
готовые копии собирает `python scripts/export_1c_brief.py`; тесты сверяют их с настоящим API
(`tests/test_1c_formats.py`), поэтому пример не может разойтись с кодом.

> **Вход в обмен — по ключу.** Владелец сам создаёт ключ в админке («Интеграция»), отдаёт его
> программисту и в любой момент может отключить. Старый вход по логину/паролю из `.env`
> (`INTEGRATION_PASSWORD`) продолжает работать.

## 1. Как работает сайт: по поставкам (инвойсам)

Магазин оптовый, поэтому остатки и цены ведутся **по поставкам**: у каждой партии цветов своя цена,
свой рейс и своя дата.

* 1С присылает инвойсы (`supplies/sync`) — товар, **цену** и **количество** по каждой строке.
  Пока инвойс в пути (`in_transit`), клиенты видят его как «Товары в пути» и делают предзаказ.
  Когда инвойс оприходован (`received`), его строки встают на полку: каждая — **отдельной карточкой**
  с пометкой «Поставка № … от …», а в `quantity` лежит **остаток партии**.
* Клиент заказывает конкретную позицию конкретной поставки. В заказе для 1С у каждой строки
  есть `supply` (id инвойса в 1С, номер, дата) — по нему 1С списывает товар из нужной партии.
* Режим «просто интернет-магазин» (товары без инвойсов) тоже есть: строки `products/sync` с `price` и
  `quantity` продаются «без поставки» (служебная партия «остаток без поставки»).

Названия полей одинаковы во всём обмене: `price` — цена за **штуку** (стебель), `quantity` — количество
в **штуках**, `sum` — сумма, `total` — итог. Упаковок в обмене нет: сайт продаёт целыми упаковками сам
(`package_size` — штук в упаковке). Старые названия (`price_per_stem`, `stock_packs`, `stock_stems`,
`quantity_packs`, `quantity_stems`) не принимаются: строка вернётся в `errors` с подсказкой.

| Данные | Главный источник | Направление |
|---|---|---|
| Инвойсы: товар, цена, остаток партии | **1С** | 1С → сайт (`supplies/sync`) |
| Карточки товаров, фото | **1С** (по желанию) | 1С → сайт (`products/sync`, `products/photo`) |
| Заказы клиентов | **сайт** | сайт → 1С (`orders/export`, потом `orders/ack`) |
| Статусы заказов | **1С** (проводит документы) | 1С → сайт (`orders/status`) |
| Персональные скидки, id контрагентов | **1С** | 1С → сайт (`clients/sync`) |
| Регистрация клиентов и их одобрение | **менеджер на сайте** | 1С только читает (`clients/export`) |

Почему регистрация остаётся на сайте: клиент сам задаёт пароль, а допуск к оптовым ценам решает
менеджер. Через обмен 1С **не может** создать клиента или выдать ему доступ — только поменять скидку.

## 2. Подготовка и проверка связи

1. Владелец: админка → **«Интеграция»** → «Создать ключ» (по желанию — список IP-адресов
   сервера 1С). Ключ выглядит как `dnt_…` и показывается один раз. Пока нет ни одного
   ключа (и не задан старый пароль) — обмен отключён, ответ `503`.
2. С любого компьютера (нужен только Python):

```bash
python scripts/onec_smoke_test.py https://dianthus-opt.ru dnt_ВАШ_КЛЮЧ
```

Скрипт проверяет ключ, связь, сертификат и показывает число товаров/заказов. С ключом `--write` он
отправляет служебную карточку «ТЕСТ-ОБМЕН-1С» без цены и количества (на витрине её не видно, в справочнике
админки — видно).

3. Запросы идут по **HTTPS**. Ключ можно передать тремя способами: заголовком `X-API-Key: dnt_…`,
   заголовком `Authorization: Bearer dnt_…` или паролем в HTTP Basic (логин — любой, пароль — ключ;
   удобно для `HTTPСоединение` 1С). Не используйте обмен по `http://` через интернет: ключ уйдёт открытым текстом.
4. Состояние обмена владелец видит в админке («Интеграция»): плашка «работает / не работает», время
   последней связи и загрузки, журнал обращений 1С с объяснением ошибок на простом языке.
5. Лимиты: 120 запросов в минуту с одного IP, тело запроса — до 40 МБ.

## 3. Рекомендуемый порядок обмена (задание по расписанию, каждые 10–15 минут)

```
1. GET  /api/1c/orders/export?new=1      забрать новые заказы
2. создать в 1С «Заказ клиента» по каждому (номер «САЙТ-<id>»), списать из партии supply
3. POST /api/1c/orders/ack               подтвердить, что заказы получены
4. POST /api/1c/supplies/sync            отправить инвойсы и остатки партий (уже с учётом шага 2!)
5. POST /api/1c/orders/status            сообщить новые статусы (проведён, отгружен, отменён)
```

**Почему именно в таком порядке.** Если сначала отправить остатки, а потом забрать заказы, то заказ,
оформленный клиентом между этими шагами, ещё не вычтен из остатка 1С — выгрузка «вернёт на полку»
проданные упаковки, и сайт может продать их ещё раз. Когда заказы забираются **до** расчёта остатков
и в 1С под них сделан резерв, отправляемые остатки уже честные.

Раз в сутки (ночью) полезно слать **полный список** (`full=1`, раздел 6), чтобы закрыть поставки,
которых в 1С больше нет. Скидки клиентов (`clients/sync`) — по необходимости, например, раз в сутки.

### Страховка от перепродажи (необязательная)

Если в `.env` задать `ONEC_RESERVE_UNEXPORTED=1`, то при загрузке остатков сайт сам **вычитает**
заказы, которые 1С ещё не подтвердила через `orders/ack`. Это закрывает «окно» между шагами 1 и 4
даже тогда, когда 1С его не учитывает. Включайте, **только если 1С действительно вызывает
`orders/ack`** — иначе подтверждения не придут, и остатки будут занижены.

## 4. Методы API

Базовый адрес: `https://ВАШ-ДОМЕН/api/1c`. Везде ключ (раздел 2, п. 3), тело — JSON в **UTF-8**
(`Content-Type: application/json; charset=utf-8`; BOM в начале допускается).

| Метод | Что делает | Описание формата |
|---|---|---|
| `GET /ping` | проверка связи и ключа | `1c-docs.json` → `ping` |
| `POST /supplies/sync` | инвойсы: в пути / оприходован / отменён; остаток партии | `supplies_sync` |
| `POST /products/sync` | карточки товаров; с `price` и `quantity` — остаток «без поставки» | `products_sync` |
| `POST /products/photo` | фото товара (тело — сама картинка) | `products_photo` |
| `GET /orders/export` | заказы сайта (`?new=1` — не забранные; `?format=csv`) | `orders_export` |
| `POST /orders/ack` | «заказы получены» | `orders_ack` |
| `POST /orders/status` | статусы заказов, номер документа 1С, комментарий | `orders_status` |
| `GET /clients/export` | клиенты (контрагенты) сайта | `clients_export` |
| `POST /clients/sync` | id контрагента в 1С, скидка, адрес | `clients_sync` |
| `GET /products/export` | справочник товаров сайта (без цен и остатков) | `products_export` |
| `GET /dictionaries` | виды, цвета, рост, страны (только чтение) | `dictionaries` |

Для старых версий 1С без JSON есть таблицы **CSV**: прайс принимается как `POST /products/sync?format=csv`,
заказы и товары выгружаются как `?format=csv[&encoding=cp1251]`, а подтверждения и статусы можно слать
в адресе, без тела. Инвойсы (`supplies/sync`) принимаются только в JSON. Подробности — в памятке.

## 5. Как сопоставляются товары

Порядок поиска товара на сайте для строки из 1С (инвойса или `products/sync`):

1. по `id` (идентификатор из 1С) — точное совпадение;
2. по `barcode` (штрихкод);
3. по `sku`;
4. по точному названию.

Шаги 2–4 применяются, только если найденный товар **не принадлежит другому идентификатору 1С**:
два разных товара 1С с одинаковым названием не склеиваются. Товар, заведённый на сайте вручную
(без id из 1С), при первой выгрузке «усыновляется» по названию, и ему проставляется id.

Поэтому: **задавайте `id` всегда** (код или GUID номенклатуры) — тогда переименование товара в 1С
не создаст дубль.

## 6. Полный список и проверка без сохранения

Без `full` сайт только добавляет и обновляет то, что прислали. Инвойс, удалённый или давно
распроданный в 1С и **не присланный** в очередной раз, остался бы на сайте. Для этого есть полный список:

```
POST /api/1c/supplies/sync?full=1       (или "full": true в теле)
```

Все поставки из 1С, которых **нет** в этой выгрузке и которые ещё в пути или имеют остаток, закрываются:
их строки снимаются с полки. Правила безопасности:

* присылайте **все** такие поставки **одним** запросом. Если делите на части, `full` не используйте;
* пустой полный список ничего не закрывает (в ответе — предупреждение);
* ручные поставки и «остаток без поставки» полный список не трогает;
* в пути забытый инвойс, которого 1С 21 день не присылала, сайт закрывает сам.

То же для товаров «без поставки»: `products/sync` с `"full": true` снимает с полки позиции «без поставки»,
которых нет в выгрузке (пустой полный снимок отклоняется: `400`); на инвойсы он не влияет.

### Сначала проверка без сохранения (`dry_run`)

Любую выгрузку можно сначала отправить с `?dry_run=1` (`supplies/sync`, `products/sync`, `clients/sync`;
для полного списка — `?dry_run=1&full=1`). Сайт выполнит все те же расчёты и вернёт обычный ответ с
`"dry_run": true`, но **ничего не запишет**. Так видно заранее:

* сколько поставок и товаров будет **создано** и сколько **обновлено** — если создаётся почти всё, а обновляется
  почти ничего, то `id`/`sku` из 1С не совпали с товарами на сайте, и настоящая загрузка завела бы дубли;
* сколько поставок закроет полный список (`closed`);
* какие строки с ошибками (`errors`) и предупреждения.

В админке то же: на странице «Интеграция» у загрузки файла есть галочка «Только проверить». Правило для
первого запуска: проверка → смотрим цифры → настоящая загрузка.

## 7. Статусы: как сопоставить с документами 1С

Пример соответствия (подберите под ваши бизнес-процессы):

| В 1С | Статус на сайте |
|---|---|
| «Заказ клиента» создан, не проведён | `Новый` |
| Проведён, товар зарезервирован | `Подтверждён` |
| Идёт сборка | `В работе` |
| «Реализация товаров» проведена, отгружено | `Отправлен` (понимается и «Отгружен») |
| Оплачено и закрыто | `Выполнен` |
| Заказ закрыт без отгрузки | `Отменён` |

Привычные названия понимаются (регистр и «ё» не важны): «Отгружен» = Отправлен, «Доставлен» = Выполнен,
«В обработке» = В работе. Комментарий 1С (`comment`) сохраняется в заметке сотрудников к заказу.
Отмена и возобновление отменённого заказа автоматически пересчитывают остаток той поставки, из которой
взят товар, а при следующей выгрузке инвойсов сайт получит от 1С верные цифры.

## 8. Переход на 1С: ручные поставки и дубли

До подключения 1С остатки на сайте ведутся вручную через «Поставки». Если после подключения один и
тот же товар одновременно лежит на полке и из ручной партии, и из инвойса 1С (или «без поставки»), в
каталоге он виден **дважды** (а цены могут отличаться). Ответ `products/sync` сообщит об этом в `warnings`.

Порядок перехода:

1. В админке → «Поставки» → **«Снять с полок»** для всех ручных партий, которые на самом деле уже учтены в 1С.
   (Машины «в пути» для предзаказов оставьте — они на полки не попадают.)
2. Отправьте из 1С инвойсы: **в пути** и **оприходованные с остатком**.
3. Дальше остатки ведёт только 1С; ручные поставки в админке нужны для товара, которого нет в 1С.

Разгрузка ручной поставки **не снимает** с полки остатки 1С и инвойсы, но и не заменяет их: по одному и
тому же товару выбирайте один источник.

## 10. Безопасность

* Только HTTPS. Если 1С не принимает сертификат Let's Encrypt, установите на сервере 1С корневой
  сертификат **ISRG Root X1** в «Доверенные корневые».
* Ключ — 160 бит случайности; на сайте хранится только его хэш, поэтому показать ключ повторно нельзя.
  Утёк или потерян — отключите в админке («Интеграция») и создайте новый: это занимает секунды и не
  требует доступа к серверу.
* Ключ можно привязать к IP-адресам сервера 1С (при создании) — с других адресов он не сработает
  (ответ `403`). Дополнительно можно ограничить доступ в nginx: в `nginx/site_https.conf`, в блоке
  `location /api/1c/`, раскомментируйте `allow <IP>; deny all;`, затем `bash scripts/update.sh`.
* Старый общий пароль (`INTEGRATION_PASSWORD` в `.env`) лучше убрать, когда обмен по ключу заработал:
  ключей может быть несколько (по одному на подрядчика), и каждый отключается отдельно.
* Каждое обращение 1С записывается в журнал обмена (админка → «Интеграция»; хранится 60 дней). Неверные
  ключи с одного адреса схлопываются в одну строку со счётчиком; с одного IP не более 120 запросов в минуту.
* Смены скидок и статусов через обмен попадают в «Журнал действий» (`/admin/audit`, автор — «1С / система»).
* Программисту 1С **не нужен и не выдаётся** доступ на сервер: инвойсы, заказы, статусы и фото идут через
  этот же ключ.

## 11. Диагностика

| Симптом | Причина и что делать |
|---|---|
| `401` | неверный или отключённый ключ (в журнале админки — «неверный ключ или пароль»). Создайте новый ключ |
| `403` | ключ привязан к другим IP-адресам. Сообщите владельцу адрес, с которого работает 1С |
| `503` «не настроен» | в админке («Интеграция») нет ни одного ключа и не задан старый пароль |
| `400` «Тело запроса не разобрать как JSON» | тело — не JSON или не UTF-8 (например, Windows-1251). Отправляйте UTF-8 |
| `413` | слишком много данных за раз — разбейте выгрузку (без `full`) |
| `400` «Полный снимок без товаров» | выгрузка вернулась пустой — проверьте запрос к номенклатуре в 1С |
| `errors`: «поле price_per_stem теперь называется price» | в коде 1С остались прежние названия — замените на `price` и `quantity` |
| `errors`: «нет price …» / «нет quantity …» | в строке нет цены продажи или количества в штуках |
| инвойс не появился на сайте | у нового инвойса нет ни одной подходящей строки (смотрите `errors` и `warnings`) |
| в каталоге товары дважды | раздел 8: ручные партии или «остаток без поставки» ещё на полке |
| сайт продал больше, чем есть | раздел 3: порядок «заказы → остатки», либо `ONEC_RESERVE_UNEXPORTED=1` |
| таймаут на больших выгрузках | у nginx для `/api/1c/` таймаут 5 минут; увеличьте таймаут в 1С |
| ошибка сертификата в 1С | раздел 10: корневой сертификат ISRG Root X1 |

Логи сервера: `docker compose logs -f app` (строки «1С sync: …»).

## 12. Чего обмен не делает (осознанно)

* не создаёт клиентов и не одобряет заявки;
* не передаёт сайту банковские платежи и накладные (только статусы);
* не создаёт документы в 1С (их создаёт 1С по заказу);
* не скачивает фото сам — 1С присылает файл отдельным запросом (`products/photo`) или ссылки.

## 13. Если из 1С нельзя ходить в интернет: файлы

Обмен по сети не обязателен. Запасной путь без программирования:

* **Каталог.** Выгрузите из 1С прайс-лист в Excel (`.xlsx`/`.xls`) или CSV (колонки вроде
  «Артикул, Штрихкод, Наименование, Вид, Цвет, Рост, Цена опт., Остаток, В пач., Страна») и загрузите в
  админке: «Интеграция» → «Загрузка из файла». Остаток из файла продаётся «без поставки». Правила те же, что у
  обмена по сети: плохие строки пропускаются с понятным описанием, пустые ячейки не затирают прежние
  данные, цену можно выбрать из нескольких колонок («Цена опт.», «Мелкий опт»), остаток и цену можно
  считать «в штуках» или «в упаковках». Кнопка «Загрузить как полный каталог» снимает с полки всё, чего в
  файле нет.
* **Заказы.** Там же: «Заказы для 1С вручную» — скачать CSV (одна строка = одна позиция, с колонками
  поставки), загрузить в 1С, затем нажать «Я загрузил их в 1С», чтобы заказы не выгружались повторно.
* Загрузка файла попадает в тот же журнал обмена («файл из админки»).
